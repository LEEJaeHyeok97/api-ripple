# 회고: 명세 기반 LLM 개발

이 프로젝트는 [명세](../spec.md)를 Claude Code에 주고 함께 개발했다. 이 문서에는 지시나 명세가 모호해서
LLM이 되묻거나 잘못 해석한 경우를 사실대로 적는다. "LLM이 명확히 이해할 수 있는 Spec이란 무엇인가"를 돌아보는 자료다.

각 항목은 다음 순서로 적는다.
원래 문장 → LLM의 해석 → 실제 의도 → 처음부터 명확했으려면 이렇게 고친다.

---

## 2026-11-15 · 작업 방식이 명세에 없었다

- **원래 문장**: (첫 지시) 명세만 붙여 넣음. 7장 "각 단계는 테스트가 통과하는 상태로 끝내고 커밋한다", 8장 "커밋은 마일스톤 단위 이상으로 잘게".
- **LLM의 해석**: 마일스톤마다 멈추지 않고 M1부터 차례로 구현하면 된다고 봤다. 커밋은 main 브랜치에 바로 했다. 명세에 브랜치, PR, 보고 시점에 대한 말이 없었기 때문이다. M1·M2를 커밋하고 M3 중간까지 진행했다.
- **실제 의도**: 저장소가 이미 외부(지원서)에 공개된 상태였다. main은 항상 CI가 통과해야 하고, 마일스톤마다 브랜치와 PR을 거쳐야 했다. 마일스톤마다 멈추고 보고받기를 원했다. 첫인상용 M0(README, LICENSE 등)을 가장 먼저 해야 했다.
- **고친다면**: 명세에 "작업 방식" 절을 둔다. 브랜치 전략, 머지 방식, 보고 시점("마일스톤마다 멈추고 승인을 기다린다"), 그리고 저장소가 이미 공개되어 있다는 맥락을 적는다. 기능 명세와 작업 절차를 분리해서 둘 다 적는다.
- **결과**: 기존 커밋은 `wip/pre-m0` 브랜치로 옮겼다. main은 빈 초기 커밋부터 다시 시작했다.

## 2026-11-16 · "SPEC.md를 교체했다"는데 저장소에 파일이 없었다

- **원래 문장**: "SPEC.md를 새 버전으로 교체했어. 이전 버전 기준으로 작업한 게 있다면 새 SPEC.md와 차이를 먼저 정리해서 보고하고"
- **LLM의 해석**: 저장소나 상위 폴더에 `SPEC.md` 파일이 있을 거라고 보고 찾았다. 없어서 차이를 정리하지 못하고 멈춘 뒤 위치를 물었다.
- **실제 의도**: 새 명세는 다음 메시지에 텍스트로 붙여 넣어 전달되었다.
- **고친다면**: 명세의 위치(파일 경로 또는 "아래에 붙인다")와 버전을 명시한다. 명세 상단에 버전·날짜를 두면 이전 버전과 비교하기도 쉽다.

## 2026-11-16 · 저장소 이름과 명세의 Action 경로가 다르다

- **원래 문장**: 명세 6.8 `uses: LEEJaeHyeok97/config-guard/action@v0`. 저장소 이름은 `api-ripple`이다.
- **LLM의 해석**: 둘 중 하나를 맞춰야 한다고 보고 물었다. "이름은 맘에 듬 그냥 진행"이라는 답을 받았다. 저장소 이름(`api-ripple`)을 유지하고, 제품 이름은 `config-guard`로 두는 것으로 해석했다.
- **실제 의도**: 해석이 맞았다. 저장소 이름은 `api-ripple`을 유지하고, Action 경로는 `LEEJaeHyeok97/api-ripple/action@v0`로 쓴다 (2026-11-16 확인). 다만 "이름은 맘에 듬"이 어느 이름을 가리키는지 한 번 더 물어야 했다.
- **고친다면**: 명세에 저장소 이름과 제품 이름을 따로 적는다 (예: "저장소: api-ripple, 도구 이름: config-guard"). 외부에 노출되는 식별자(플러그인 ID, Action 경로)는 표로 한 번에 정의한다.
